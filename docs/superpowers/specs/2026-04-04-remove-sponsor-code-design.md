# 取消赞助码与 VIP 限制设计

## 1. 背景

当前 go-stock 在产品层存在一套“赞助码/VIP”机制，既影响界面展示，也影响功能可用性。实际限制点包括：

- 桌面端设置页的赞助码输入与校验入口
- 关于页的 VIP 等级、有效期、赞助计划与权益说明
- 桌面端多个功能入口的 `vipLevel` 判定与告警提示
- `ai-assistant-web` 子服务的 `VIP2` 接口准入限制
- README 与使用手册中的赞助码和 VIP 分级文案

本次目标不是保留赞助体系但放宽限制，而是将产品层的赞助码/VIP 概念整体移除，使软件以“功能全部开放”的形态对外呈现。

## 2. 目标

本次改动需要同时满足以下目标：

- 软件全部功能默认可用，不再依赖赞助码或 VIP 等级
- 界面中不再出现赞助码输入、VIP 等级、VIP 到期时间、赞助计划、权益分级等内容
- `ai-assistant-web` 默认可访问，不再要求 `VIP2`
- 文档中不再宣称某些功能仅限 VIP
- 保持本地数据库与历史配置兼容，不因删除赞助逻辑破坏旧用户环境

## 3. 非目标

以下内容不在本次范围内：

- 不修改数据库 schema，不迁移或删除 `settings.sponsor_code`
- 不清理所有历史兼容代码到“完全无痕”，优先保证行为正确与兼容稳定
- 不调整“支持作者”之外的普通社区、联系方式或项目介绍结构
- 不顺带重构与赞助码无关的 AI、行情、推送或配置逻辑

## 4. 方案对比

### 方案 A：最小放开

仅去掉功能限制，尽量保留现有接口和界面结构。

优点：

- 改动最小
- 回归面较小

缺点：

- 界面与文档仍会保留赞助码/VIP 概念，产品表达自相矛盾
- 后续维护人员仍容易误判功能是否受限

### 方案 B：兼容式删除（推荐）

删除产品层的赞助码/VIP 入口、文案、限制和准入控制；保留底层 `sponsor_code` 字段与必要兼容接口，不做数据库迁移。

优点：

- 用户看到的软件已是“全功能开放版”
- 不破坏已有数据库和旧配置导入导出
- 改动成本与回归风险处于可控范围

缺点：

- 代码中会保留少量历史兼容字段，需要明确这是兼容保留而非有效业务逻辑

### 方案 C：彻底清除

连配置模型、接口、数据库字段和全部历史逻辑一并删除。

优点：

- 代码最干净

缺点：

- 对旧数据和旧配置兼容性风险最高
- 会扩大本次改动范围，不符合“先稳定释放全部功能”的优先级

### 结论

采用方案 B。优先保证产品层全面去赞助化，同时保留数据兼容性，避免对现有用户环境造成破坏。

## 5. 总体设计

本次设计遵循三个原则：

- 正确性优先：所有原先受 VIP 限制的功能必须默认可用
- 可维护性优先：界面、接口、文档与实际行为保持一致，不保留误导性入口
- 可观测性优先：保留兼容接口时，返回结果应明确反映“当前版本已开放”，避免后续调用方误判

整体实现分为四层：

1. 后端兼容层
2. Web 子服务准入层
3. 前端展示与交互层
4. 文档层

## 6. 后端设计

### 6.1 App 暴露接口

`app.go` 中现有与赞助相关的方法将改为兼容模式：

- `CheckSponsorCode`
  - 不再执行真实校验
  - 返回兼容成功结果，或明确返回“当前版本无需赞助码”
  - 不再作为保存配置的前置条件
- `GetSponsorInfo`
  - 返回兼容的开放状态
  - 前端若仍存在旧调用，也不会因空赞助码导致界面异常
- `GetEffectiveSponsorVip`
  - 返回“已开放”兼容结果
  - 不再作为功能授权依据

设计原因：

- 直接删除这些接口会牵连 Wails 绑定与多个前端调用点，增加回归风险
- 先将其退化为兼容接口，可以在较小改动范围内稳定解除限制

### 6.2 VIP 判定逻辑

`isVip` 及其关联调用不再承担授权职责。

处理原则：

- 不再根据 `sponsorCode`、有效期、等级决定功能是否可用
- 原本依赖 `isVip` 的功能分支统一走开放路径
- 若某些返回结构仍需 `vipLevel` 字段，则返回固定兼容值，避免前端类型或判断分支出错

### 6.3 更新下载逻辑

当前版本中，更新下载地址会根据 VIP 状态切换 GitHub/CDN 链接。本次统一采用公开可用的下载逻辑，不再按赞助等级分流。

设计原因：

- 既然产品已取消赞助机制，就不应继续基于 VIP 状态提供不同更新路径
- 统一路径可减少“本地显示已开放，但更新行为仍分级”的不一致问题

## 7. AI Assistant Web 设计

`ai-assistant-web/server.go` 中现有 `requireVip2` 和 `/api/vip-status` 需要改造。

### 7.1 准入控制

- `requireVip2` 改为默认放行，或删除其阻断行为
- 所有受其保护的接口默认可访问：
  - `/api/ai-configs`
  - `/api/prompts`
  - `/api/session`
  - `/api/chat/summary-stream`
  - `/api/share`

### 7.2 状态接口

- `/api/vip-status` 保留，但返回兼容的“已开放”结果
- 返回语义应反映“当前版本无需 VIP 即可访问”，避免 Web 前端仍显示拒绝文案

设计原因：

- Web 子服务已明确存在独立的 VIP2 限制，这是当前功能释放的关键阻断点
- 保留状态接口可以减少前端联动改动，但其语义必须从“授权校验”改为“兼容开放状态”

## 8. 前端设计

### 8.1 设置页

文件：`frontend/src/components/settings.vue`

改动：

- 删除赞助码输入框、验证按钮和帮助说明
- 删除保存配置时对 `CheckSponsorCode` 的依赖
- 保留其他设置项与整体布局稳定

设计原因：

- 若功能已开放，设置页继续保留赞助码入口会直接制造误导
- 删除该区域后，用户保存设置不应再被无关流程阻断

### 8.2 关于页

文件：`frontend/src/components/about.vue`

改动：

- 删除 VIP 等级徽标
- 删除 VIP 到期时间展示
- 删除赞助计划、赞助等级、权益说明表格
- 删除“赞助码获取方式”等文案
- 删除与 VIP 状态相关的初始化逻辑和过期提示
- 保留项目介绍、社区链接、作者信息、普通联系方式等非赞助内容

设计原因：

- 用户明确要求连“赞助计划/VIP 等级/权益表/赞助码获取方式”一起删除
- 关于页是最直接的产品介绍入口，必须与“全部功能开放”保持一致

### 8.3 功能入口解锁

以下组件中的 `vipLevel` 限制与提示需要移除：

- `frontend/src/components/FloatingAiAssistant.vue`
- `frontend/src/components/FloatingAgentAssistant.vue`
- `frontend/src/components/stock.vue`
- `frontend/src/components/TradingRecordManager.vue`
- `frontend/src/components/allStockList.vue`
- `frontend/src/components/aiRecommendStocksList.vue`

改动原则：

- 删除 `vipLevel` 获取逻辑及其加载状态
- 删除“未开通VIP”“仅限VIP2”“权限不足”等提示
- 功能入口直接按用户操作继续执行

设计原因：

- 这些组件是当前产品层真实存在的功能门禁点
- 如果只删设置页和关于页，不删这些判断，用户仍会在关键路径上被拦截

## 9. 文档设计

需要同步修改以下文档：

- `README.md`
- `docs/go-stock使用手册.md`

改动原则：

- 删除赞助码、VIP、权益等级、专属功能等分级描述
- 将相关功能改写为默认可用
- 删除“联系作者获取赞助码后激活”等操作指引

设计原因：

- 文档必须与软件行为一致
- 若文档仍保留 VIP 限制，用户会无法判断当前版本到底是否已全部开放

## 10. 兼容性设计

### 10.1 数据库兼容

保留 `backend/data/settings_api.go` 中的 `SponsorCode` 字段，不做数据库迁移。

原因：

- 旧用户本地数据库可能已存在 `sponsor_code`
- 本次目标是解除限制，不是清理历史数据
- 保留字段可以避免导入旧配置或读取旧数据时出现失败

### 10.2 导入导出兼容

配置导入导出即使仍携带 `sponsorCode`，也不应影响当前版本运行。

处理原则：

- 导入旧配置时忽略其业务意义
- 导出配置时允许字段继续存在，避免与旧版本配置格式完全断裂

### 10.3 Wails 绑定兼容

优先保留后端兼容接口，避免立即破坏 `frontend/wailsjs/go/main/App.*` 绑定关系。

处理原则：

- 如果现有生成流程可稳定执行，可在实现完成后刷新绑定文件
- 如果生成条件不明确，则先保留兼容接口，保证前后端可正常联调

## 11. 风险与应对

### 风险 1：仍有隐藏的 VIP 判断遗漏

应对：

- 在实现前后都使用全文检索复查 `vip`、`赞助码`、`CheckSponsorCode`、`GetSponsorInfo`、`requireVip2` 等关键字
- 以功能路径回归验证替代只看代码表面删除

### 风险 2：前端删除 UI 后仍残留旧初始化逻辑

应对：

- 同步删除与 VIP 状态相关的 `ref`、`onMounted` 获取逻辑和提示代码
- 防止出现“UI 已无入口，但控制台仍报错”问题

### 风险 3：Web 子服务前端仍依赖旧的拒绝语义

应对：

- 保留 `/api/vip-status`，但统一返回开放状态
- 若前端基于该接口决定展示，也能得到一致结果

## 12. 测试与验收

本次按“先补测试，再改实现”的方式执行。

### 12.1 后端测试

至少补充以下回归测试：

- 在无赞助码时，AI Assistant Web 的受限接口可正常访问
- 赞助信息接口返回兼容开放结果，不再因空值、过期或无效码判为不可用

### 12.2 前端回归检查

重点检查以下行为：

- 设置页不再显示赞助码输入与验证
- 关于页不再显示 VIP/赞助计划/权益分级内容
- AI 助手、Agent 助手、多周期 K 线、交易记录 K 线、技术面筛选、AI 推荐相关功能可直接使用
- 页面不再弹出“未开通VIP”“VIP已到期”“仅限VIP2”等提示

### 12.3 命令约束

验证命令优先使用：

```powershell
conda run -n test ...
```

若当前环境不存在 `test` conda 环境，需要先确认仓库实际可用环境，再执行相应验证命令；在未确认前，不假设存在其他 Python 环境或前端构建方式。

## 13. 实施拆分建议

推荐按以下顺序实施：

1. 先补后端兼容测试，锁定“默认开放”的期望行为
2. 改造 `app.go` 和 `ai-assistant-web/server.go`，去掉后端与 Web 的授权门禁
3. 修改前端各组件，移除赞助码/VIP 入口与提示
4. 更新 README 与使用手册
5. 全量检索与回归验证，确认无残留门禁文案和逻辑

这样的顺序能先解除核心功能阻断，再清理展示层，最后统一文档，回归路径最清晰。
