# 修复多周期 K 线东财链路设计

## 1. 背景

当前 go-stock 的“多周期K线”由股票详情页弹窗组件 `StockLightweightKlineChart.vue` 驱动，后端通过 `GetStockEastMoneyKLine` / `GetStockEastMoneyKLinePage` 调用东方财富 `push2his.eastmoney.com` 的 K 线接口。

现象已经明确：

- 股票详情页“多周期K线”可以进入弹窗，但图表无数据
- 普通“日K”与该链路不同，不构成本次问题的直接证据
- 运行日志中持续出现东财 K 线请求 `EOF`

已确认的关键证据：

- 前端入口仍正常打开弹窗，问题不在 VIP 解锁逻辑
- `build/bin/logs/error.log` 中，多周期 K 线对应的多个周期请求都报：
  - `data/eastmoney_kline_api.go:61 HTTP error ... EOF`
  - `data/eastmoney_kline_api.go:318 GetKLineData error ... EOF`
- 同一只股票在 `1`、`15`、`30`、`60`、`101`、`102` 等多个 `klt` 上都失败，说明不是单一周期参数错误

因此，本次目标是修复东方财富多周期 K 线请求链路，而不是继续调整产品层权限或界面入口。

## 2. 目标

本次改动需要同时满足以下目标：

- 股票详情页“多周期K线”能够重新拉取并展示东财 K 线数据
- 后端能区分“网络链路失败”和“接口返回空数据”两类问题
- 当前环境下若东财请求仍失败，前端必须展示明确错误原因，不再表现为静默空白
- 不影响普通日 K、交易记录 K 线、AI、设置等无关功能

## 3. 非目标

以下内容不在本次范围内：

- 不更换东财为新的 K 线主数据源
- 不重做多周期 K 线的整体 UI 或技术指标逻辑
- 不重构全部行情网络层，只修复与东财多周期 K 线直接相关的链路
- 不顺带修改赞助码/VIP 兼容逻辑

## 4. 方案对比

### 方案 A：只增强前端错误提示

仅保留现有后端实现，前端在空数据时显示更明确的错误文案。

优点：

- 改动小
- 可以快速避免“空白不可诊断”

缺点：

- 不能恢复功能
- 根因仍留在后端请求链路

### 方案 B：修复东财请求链路并补充错误透出（推荐）

针对 `EastMoneyKLineApi` 的请求方式做根因修复，同时保留前端错误透出。

优点：

- 能恢复多周期 K 线功能
- 后端和前端的失败语义会更清晰
- 改动集中在问题链路，风险可控

缺点：

- 需要补充网络层诊断与验证
- 需要处理当前 `EOF` 与 cookie / transport / 压缩协商之间的关系

### 方案 C：切换备用数据源

彻底绕过东方财富链路，改由其他来源提供多周期 K 线。

优点：

- 可以绕开东财当前链路不稳定问题

缺点：

- 改动范围大
- 需要重做字段映射、分页、周期支持和兼容验证
- 与“修复现有功能”相比投入过高

### 结论

采用方案 B。优先修复现有东财多周期 K 线链路，同时补齐失败时的诊断与前端提示。

## 5. 根因假设

基于当前日志和最小复现结果，本次先围绕以下假设排查与修复：

### 假设 1：当前 HTTP 请求方式与东财接口的连接要求不兼容

表现：

- 请求直接在 `Get` 阶段返回 `EOF`
- 不是 JSON 解析失败，也不是接口业务错误码

优先排查项：

- 是否因为默认 transport/连接复用导致服务端直接断开
- 是否因为请求压缩协商不稳定，导致连接被服务端提前关闭
- 是否因为未显式使用浏览器 cookie 或关键 header，被东财边缘风控直接断流

### 假设 2：请求上下文没有复用项目已存在的东财 cookie 能力

当前 `fetchKLineJSONBytesByHTTP` 中与 chromedp cookie 相关逻辑被注释掉，说明代码历史上已经意识到该接口可能依赖 cookie 或浏览器上下文。

优先排查项：

- 恢复 cookie 路径后是否能消除 `EOF`
- 在配置了浏览器路径时，是否应优先尝试带 cookie 的请求

### 假设 3：失败信息在前端被过度吞掉

当前前端对后端抛错与空数据处理偏弱，导致用户只能看到“没图”而不知道是请求失败。

优先排查项：

- 后端失败时是否返回了可识别错误
- 前端空数据与异常分支是否应区分提示

## 6. 总体设计

本次设计分三层实施：

1. 后端请求诊断层
2. 后端请求修复层
3. 前端错误可见层

### 6.1 后端请求诊断层

文件重点：

- `backend/data/eastmoney_kline_api.go`
- `backend/data/eastmoney_kline_chromedp.go`

设计原则：

- 先让失败可观测，再收敛修复
- 日志要能回答“请求如何发出去、失败发生在哪一步、是否使用了 cookie/代理”

需要补充的诊断信息：

- 当前请求的股票代码、`klt`、`limit`
- 是否命中了浏览器路径配置
- 是否带 cookie 发起请求
- 请求失败阶段：连接错误、超时、HTTP 非 200、gzip 解压失败、JSON 解析失败
- 失败原因摘要，避免只留下泛化的 `EOF`

### 6.2 后端请求修复层

修复策略按以下顺序收敛：

#### 第一层：稳定 HTTP 客户端配置

目标：

- 降低因连接复用、压缩协商或默认 transport 差异导致的 `EOF`

候选动作：

- 为东财 K 线请求配置明确的 `Transport`
- 明确 `DisableCompression` 与 gzip 处理策略，避免“声明支持但处理不一致”
- 根据当前环境决定是否关闭 HTTP/2 或限制连接复用
- 保持请求头尽量贴近浏览器请求，但不堆叠无效头

#### 第二层：恢复可控的 cookie 请求路径

目标：

- 在需要浏览器上下文时，优先复用项目已有的 chromedp cookie 能力

设计原则：

- 默认仍以纯 HTTP 路径为主
- 若配置了 `BrowserPath`，允许在东财 K 线请求中带 cookie 重试
- 不能每次都无条件启动浏览器，优先使用现有缓存能力

推荐策略：

- 首次纯 HTTP 请求失败且错误属于连接类异常时，若浏览器环境可用，则使用 cookie 路径进行一次重试
- 若重试成功，则返回数据
- 若重试失败，则保留明确错误信息

#### 第三层：错误语义收敛

目标：

- 区分“接口空数据”和“请求失败”

设计原则：

- 后端不要把所有失败都降格为“空数组”
- 对前端可见的接口应在失败时携带明确 message

本次推荐做法：

- `GetStockEastMoneyKLine` / `GetStockEastMoneyKLinePage` 仍保持现有返回结构兼容，但在日志中输出更清晰错误
- 前端若收到空数据且后端已记录连接失败，应显示“东财 K 线请求失败，请稍后重试或检查浏览器路径/网络环境”

## 7. 前端设计

文件重点：

- `frontend/src/components/StockLightweightKlineChart.vue`

当前问题：

- 组件区分了异常和空数据，但异常经常被吞成通用空白体验

改动原则：

- 有错误时优先显示错误文案
- 空数据时显示“暂无 K 线数据”
- 网络链路失败时显示“东财数据源请求失败”的明确提示

推荐行为：

- `loadData()` 捕获异常后，保留当前 `errorText`
- 若后端返回空数组但当前请求属于典型失败场景，则将 `errorText` 设为“东财 K 线请求失败”
- 保持现有图表和技术指标结构不变，不重做 UI

## 8. 兼容性设计

### 8.1 接口兼容

不修改 Wails 暴露方法名：

- `GetStockEastMoneyKLine`
- `GetStockEastMoneyKLinePage`

这样可以避免影响现有前端绑定和调用点。

### 8.2 行为兼容

- 成功路径下仍返回当前使用的 `[]KLineData`
- 现有多周期图、历史左拖分页、实时刷新逻辑继续使用相同数据结构
- 普通日 K 功能不切换到东财链路，也不被本次修改影响

## 9. 风险与应对

### 风险 1：修 transport 后仍然 `EOF`

应对：

- 保留带 cookie 的二次重试路径
- 对失败进行分类日志，避免继续盲猜

### 风险 2：cookie 重试引入浏览器依赖过重

应对：

- 仅在浏览器路径存在且首次 HTTP 失败时启用
- 继续复用现有 cookie 缓存，不做每次冷启动浏览器

### 风险 3：前端仍显示为空白

应对：

- 前端统一把“连接失败”和“空数据”拆开
- 补最小回归验证，覆盖至少一个失败提示场景

### 风险 4：修复过程中误伤其他行情接口

应对：

- 改动限制在东财 K 线相关文件
- 验证时重点回归普通日 K 和多周期 K，避免扩大修改面

## 10. 测试与验收

### 10.1 后端验证

至少验证以下场景：

- 指定 A 股代码请求 `101` 日 K，返回非空
- 指定 A 股代码请求 `1` 或 `15` 分钟 K，返回非空
- 未配置浏览器路径时，失败日志能明确识别请求链路问题
- 配置浏览器路径后，cookie 重试路径可触发并记录结果

### 10.2 前端验证

重点检查：

- 股票详情页点击“多周期K线”后能看到数据
- 切换日 / 周 / 分钟周期至少各成功一类
- 请求失败时弹窗内显示错误文案，而不是静默空白

### 10.3 回归边界

至少确认以下行为未回归：

- 普通“日K”仍可打开
- 股票详情页弹窗能正常关闭和重新打开
- 交易记录页 K 线弹窗不受本次修复影响

## 11. 实施拆分建议

推荐按以下顺序实施：

1. 先补 Go 层最小复现与失败分类验证
2. 在 `eastmoney_kline_api.go` 中加入诊断日志和连接修复
3. 恢复或补充带 cookie 的重试逻辑
4. 在 `StockLightweightKlineChart.vue` 中补失败提示
5. 重新验证多周期 K 线的日/周/分钟路径

这样可以先定位根因，再做最小修复，最后补齐前端可见性，避免一上来大改网络层。
