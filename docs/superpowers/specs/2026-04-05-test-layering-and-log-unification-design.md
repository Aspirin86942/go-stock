# 测试体系分层与日志一体化重构设计

## 1. 背景

当前仓库已经开始向统一日志门面收敛，但测试体系仍然明显滞后于正式运行链路，主要问题如下：

- `_test.go` 中同时混杂了纯逻辑单测、隔离集成测试、真实外网调用、系统环境探针和“打印结果后人工观察”的探索脚本
- 许多测试仍直接使用旧 `logger.SugaredLogger`，测试日志语义与正式运行日志体系脱节
- 真实外部链路测试与稳定可回归测试没有清晰边界，导致“默认应该跑什么”语义不清
- 现有 GitHub Actions 主要承担构建职责，缺少稳定的测试门禁、外部集成作业和失败产物归档
- 一部分日志相关测试已经证明了正确方向，例如跨 sink 的 `trace_id` 复用、真实落盘与 payload 断言，但这种模式尚未推广为统一规范

因此，这次需求不应被理解为“把测试里的旧 `SugaredLogger` 批量替换掉”，而应理解为：将测试体系重构为分层、可门禁、可排查、并且与正式运行日志基础设施一致的工程系统。

## 2. 已确认需求

本次设计阶段已确认以下边界：

- 用户目标是重构项目的整体测试流程，而不是只清理少量旧日志调用
- 用户希望测试覆盖是“全层次”的，不能只保留局部单元测试
- 用户明确要求保留真实链路测试，不把真实 AI、真实资讯/行情、真实抓取一概排除出测试体系
- 用户认可测试日志应与软件运行日志“有机结合”，即在需要观测链路时复用同一套日志基础设施
- 用户认可采用测试分层方案，而不是让所有真实外部链路都混入单一默认门禁
- 用户认可测试触发方式应尽量沿用现有 `go test` / `node --test` / Wails 构建流程，不额外引入复杂测试框架

## 3. 目标

本次重构需要同时满足以下目标：

- 为仓库内测试建立明确的层次边界和统一触发语义
- 让 `unit`、`component`、`integration`、`external`、`release-smoke` 五类测试各自承担清晰职责
- 让默认质量门禁稳定、可重复、可在本地和 CI 中可靠运行
- 保留真实外部链路测试，但将其从“默认 `go test ./...` 语义”中拆分出来，单独建门禁与排障策略
- 让需要观测链路的测试复用 `backend/logger` 的 sink、payload、`trace_id` 与落盘方式
- 将测试失败时的排查方式统一到“看结构化日志和 payload 产物”这一条路径上
- 逐步消除测试代码里对旧 `SugaredLogger` 的直接依赖，只保留少量兼容层验证测试

## 4. 非目标

以下内容不在本次设计范围内：

- 不把所有真实外部链路测试都强行纳入每次开发提交的默认阻塞门禁
- 不把日志文件当成普通业务正确性的主断言来源
- 不为了测试重构额外引入新的大型测试平台、全局 mock 框架或通用测试容器层
- 不要求一次性重写所有历史测试文件
- 不借测试重构之机大规模改造业务代码签名与模块边界

## 5. 方案对比

### 方案 A：全真实链路默认主门禁

将大部分现有测试保留为真实外部依赖测试，统一改造成默认每次都跑。

优点：

- 最接近“所有测试都是真实运行”的直觉
- 与线上行为表面上最接近

缺点：

- 对网络、交易时间窗、第三方限流、凭证、浏览器环境高度敏感
- 本地和 CI 都容易因为环境波动而变脆
- 开发反馈周期明显变长

### 方案 B：分层测试 + 统一观测

将测试拆分为 `unit / component / integration / external / release-smoke` 五层，其中前 3 层组成默认门禁，后 2 层保留为真实链路测试，但单独触发、单独排障。

优点：

- 分工清晰，可维护性最好
- 默认门禁可稳定运行，同时保留真实链路验证
- 最容易与统一日志体系结合

缺点：

- 需要团队接受“不是所有真实链路都进默认阻塞门禁”这一事实
- 需要补分类规则和 CI 结构

### 方案 C：先搭测试基础设施，再渐进清理旧测试

第一阶段先建立门槛 helper、日志产物约定和 CI 骨架，第二阶段再清理旧测试身份，第三阶段再补关键真实链路闭环。

优点：

- 对当前仓库状态最安全
- 可以避免“一次性大迁移”带来的回归风险

缺点：

- 短期内不会立即看到“所有历史测试都被收敛干净”

### 结论

目标架构采用方案 B，落地节奏采用方案 C。

原因是：当前仓库中大量 `_test.go` 文件并不具备稳定门禁属性，先做分层和基础设施，再做历史清理，能在正确性、可维护性和可观测性之间取得更稳妥的平衡。

## 6. 测试分层模型

本次设计将测试固定为五层，但只暴露三类主要触发入口，避免分类细而入口乱。

### 6.1 五层测试职责

#### `unit`

职责：

- 纯逻辑、纯转换、纯计算
- 不触网
- 不依赖真实数据库文件、真实 GUI、真实浏览器、真实第三方状态

要求：

- 快
- 稳定
- 可并行
- 任何提交都必须通过

#### `component`

职责：

- 测单个模块与基础设施接线
- 外部依赖仍保持本地隔离
- 主要依赖 `t.TempDir()`、`httptest`、临时 sqlite、本地假服务

典型适用场景：

- `backend/logger`
- `backend/db`
- `ai-assistant-web`
- Wails 桥接 payload 规范

#### `integration`

职责：

- 测真实模块组合，但尽量把不确定性限制在仓库或本地隔离环境内

典型适用场景：

- HTTP -> service -> DB -> logger
- task -> AI sink -> DB sink -> payload spill
- 前端错误桥接 -> frontend sink -> error sink

该层应默认进入质量门禁，因为这是“测试日志和运行日志结合”的核心闭环层。

#### `external`

职责：

- 测真实外网、真实第三方接口、真实 AI、真实网页抓取、真实行情源等

特点：

- 接受波动
- 需要凭证或环境
- 需要与默认门禁分离

#### `release-smoke`

职责：

- 测打包产物、Wails 启动、关键页面加载、桥接调用、前端错误回传、关闭日志等发布前行为

特点：

- 更接近发布验收
- 不适合作为普通包级测试默认门禁

### 6.2 三类主入口

五层测试通过三类主入口触发：

- `default`
  - 覆盖 `unit + component + integration`
- `external`
  - 覆盖真实外部依赖链路
- `release`
  - 覆盖发布冒烟链路

这样做的原因是：测试职责需要细分，但开发者和 CI 的执行入口应尽量粗粒度且稳定。

## 7. 测试日志与运行日志的一体化模型

### 7.1 总体原则

本次设计不是要求所有测试都直接写正式运行日志，而是要求：

- 只要测试目标涉及链路观测，就必须复用 `backend/logger` 的统一基础设施
- 只要测试目标只是普通业务正确性，就优先使用普通断言与 `t.Log`，不把日志当作主断言

### 7.2 不同测试层的日志策略

#### `unit`

- 默认使用 `t.Log` / `t.Logf`
- 不强制接入统一运行日志体系

#### `component / integration / external / release-smoke`

只要测试目标涉及以下内容之一，就统一初始化测试 runtime：

- sink 落盘
- `trace_id` 传播
- payload spill
- 错误链路聚合
- Wails / HTTP / DB / 任务 / AI / 前端错误桥接

### 7.3 测试日志目录布局

建议统一落到测试专属目录，例如：

- `artifacts/testlogs/<test_run_id>/<package>/<test_case>/logs/*.log`
- `artifacts/testlogs/<test_run_id>/<package>/<test_case>/logs/payloads/...`

若本地快速执行不需要持久保留，也可先落到 `t.TempDir()`，但 CI 失败场景必须能将其提升为可归档产物。

### 7.4 复用现有日志语义

测试链路应继续复用现有统一 sink：

- `SinkApp`
- `SinkError`
- `SinkHTTP`
- `SinkAI`
- `SinkTask`
- `SinkDB`
- `SinkFrontend`
- `SinkPanic`

同时继续复用现有链路字段语义：

- `trace_id`
- `span_id`
- `app_session_id`
- `source`

### 7.5 测试身份字段

为避免覆盖既有 `source` 语义，本次设计不建议简单将 `source` 强制改写为 `test`。  
原因是：`source` 当前承担链路入口语义，例如 `http`、`task`、`wails-frontend`，如果统一覆盖为 `test`，会损失排障价值。

因此建议保留 `source` 原语义，并额外增加最小测试身份字段：

- `execution_mode=test`
- `test_run_id`
- `test_suite`
- `test_case`

这样可以同时回答两个问题：

- 这条日志来自哪条真实链路入口？
- 这条链路是由哪次测试触发的？

### 7.6 日志在测试中的职责边界

日志只承担两类职责：

- 验证日志系统本身是否工作正常
- 验证关键链路是否具备可观测性和可追踪性

明确禁止以下误用：

- 用扫日志代替普通业务结果断言
- 用大量结构化日志输出掩盖断言缺失
- 普通业务测试仍然只打印不校验

## 8. 现有测试的迁移规则

现有测试不应按“是否用了 `SugaredLogger`”来区分，而应先按身份分类，再决定迁移动作。

### 8.1 第一类：保留并收紧

这类测试已经接近目标形态，只需补统一入口和少量字段，不应推倒重来。

典型代表：

- `backend/logger/core_test.go`
- `backend/logger/closeout_integration_test.go`
- `backend/agent/cron_task_api_test.go`
- `ai-assistant-web/server_test.go`

处理原则：

- 保留真实断言
- 继续使用 `t.TempDir()`、`httptest`、临时 sqlite 等隔离手段
- 当测试目标涉及观测链路时，接入测试 runtime
- 当测试目标只是业务正确性时，日志只作为辅助信息

### 8.2 第二类：重写为真正测试

这类文件虽然命名为测试，但当前行为更接近探索脚本。

典型代表：

- `app_test.go`
- `backend/data/openai_api_test.go`
- `backend/data/market_news_api_test.go`
- `backend/data/crawler_api_test.go`
- `backend/data/stock_data_api_test.go`

处理原则：

- 将“只打印不校验”改造成明确断言
- 能隔离的外部依赖先隔离为本地假服务、固定样本、临时数据库
- 普通输出改为 `t.Log` / `t.Logf`
- 只有当测试目标本身就是日志链路时，才使用统一 logger runtime

若某个用例在重写前仍然只能“打印出来人工看”，则它不应继续被当作默认门禁测试。

### 8.3 第三类：迁出为 `external` / `release-smoke` / `manual`

以下内容即使保留，也不应继续伪装成普通默认测试：

- 真实 AI 接口调用
- 真实新闻/行情网站抓取
- 真实系统通知、分辨率、GUI 依赖
- 强依赖交易时段、代理、第三方限流状态的行为

这类测试可以继续存在，但需要改成明确身份：

- `external`
- `release-smoke`
- 必要时 `manual-check`

### 8.4 关于旧 `SugaredLogger` 的定位

旧 `SugaredLogger` 的清理顺序应晚于测试身份清理。

原因：

- `SugaredLogger` 只是表层现象
- 真正的问题是测试身份混乱、断言不足、触发语义不清

最终目标是：

- `backend/logger` 内保留少量兼容层验证测试
- 其余测试代码不再直接依赖旧 `SugaredLogger`

## 9. 统一入口与运行方式

### 9.1 基本原则

- 继续以包内 `_test.go` 为主，不额外引入新的大型测试框架
- 测试分层主要通过运行时门槛 helper、目录语义和 CI 任务名表达
- 尽量沿用现有 `go test`、`node --test` 与 Wails 构建流程

### 9.2 门槛 helper

现有 `requireIntegrationTest(t)` 语义不足以覆盖新的分层结构，建议收敛为：

- 默认测试不加门槛，直接运行
- `requireExternalTest(t)`
  - 用于真实外部依赖
- `requireReleaseSmokeTest(t)`
  - 用于发布冒烟

这样默认 `go test ./...` 在遇到 `external` 或 `release-smoke` 测试时，会因缺少显式开关而跳过，而不是误跑。

### 9.3 不以 build tags 作为主分类手段

本次设计不建议将 build tags 作为主运行模型。

原因：

- 当前问题本质上是环境与稳定性分层，不是编译期隔离问题
- 现有仓库已采用运行时门槛模式，迁移成本更低
- 对开发者而言，环境变量与 skip 原因比 build tags 更直观

### 9.4 最小测试 runtime 初始化能力

需要提供一个最小测试 runtime 初始化能力，但必须保持职责单一。

它只负责两件事：

- 创建测试专属 `logs/` 目录
- 初始化 `backend/logger` runtime，并写入测试身份字段

它不负责：

- 统一 mock
- 统一断言
- 注入业务依赖
- 构建新的测试框架

### 9.5 测试本体与测试脚本的组织原则

本次迁移不建议将所有测试文件集中挪到单一目录。

原因：

- Go 包级 `_test.go` 与被测代码就近放置时，可维护性最高
- 就近放置更容易理解依赖、测试边界与局部夹具来源
- 如果将所有测试本体集中迁走，会削弱包边界并增加上下文切换成本

因此组织原则明确为：

- 包级 `_test.go` 保持就近放置，不做全集中迁移
- 仓库级测试入口脚本统一收口到单独目录，例如 `scripts/testing/`
- 手工验证脚本、真实外部链路编排脚本、发布冒烟编排脚本也统一收口到 `scripts/testing/` 下的子目录
- 共享测试数据优先使用 `testdata/`
- 若某份样本只服务于单个包，则优先贴近该包放置；只有跨包复用需求明确存在时，才提升为仓库级共享资源

## 10. CI 与测试产物策略

### 10.1 CI 结构拆分

建议测试工作流与现有发布构建工作流拆开，不要将两者耦合在同一个 job 内。

建议新增以下任务：

#### `test-default`

- 触发：PR / push
- 覆盖：`unit + component + integration`
- 作用：未来的主质量门禁

#### `test-external`

- 触发：`workflow_dispatch` + 定时 nightly
- 覆盖：真实外部依赖链路
- 特点：允许更长超时，保留完整日志产物

#### `release-smoke`

- 触发：发布前或显式手工触发
- 覆盖：Wails 启动、关键桥接、关键运行日志
- 特点：与正式构建流程协同，但不直接塞进现有发布构建 job

### 10.2 失败排障策略

`default` 失败时：

- 先看断言
- 若属于链路观测失败，再查看测试专属 `logs/` 与 `payloads/`

`external` 失败时：

- 必须将失败拆分为“代码回归”与“外部环境波动”两类
- 日志中应补足目标接口、HTTP 状态、超时、重试次数、限流命中等信息

### 10.3 产物归档

对 `component / integration / external / release-smoke`，CI 失败时至少应上传：

- `logs/*.log`
- `logs/payloads/**`
- 必要时的临时响应快照

### 10.4 覆盖率策略

覆盖率只对稳定层统计，即：

- `unit`
- `component`
- `integration`

不将真实外部链路混入 coverage 目标，以免覆盖率语义失真。

## 11. 落地顺序

本次重构按三阶段推进。

### 阶段一：立规则和基础设施

目标：

- 写清测试分层规范
- 建立 `requireExternalTest` / `requireReleaseSmokeTest`
- 建最小测试 runtime 和测试产物目录约定
- 搭建 CI 骨架

这一阶段不追求清完所有历史测试，只先让新规则能被执行。

### 阶段二：清理旧测试身份

目标：

- 扫描现有 `_test.go`
- 将其分成“保留并收紧 / 重写 / 迁出”
- 将“只打印不校验”的用例改造成断言，或迁到 `external` / `manual`
- 开始逐步替换测试中的旧 `SugaredLogger`
- 将仓库级测试编排脚本与历史手工探测脚本收口到统一脚本目录，而不是继续散落在包测试文件中

### 阶段三：补关键真实链路闭环

目标：

- 重点补 AI、行情、抓取、任务、前端桥接、Wails 生命周期等高风险链路
- 确保这些真实链路测试也能复用统一 `trace_id` 和 sink
- 让 CI 可以上传并排查这些链路的失败日志产物

## 12. 风险与待补充信息

已确认风险：

- 真实外部链路测试天然更慢、更脆弱，且更依赖网络和第三方状态
- 凭证、代理、浏览器能力、交易时段都会影响可重复性
- 如果过早把历史探索脚本全部纳入默认门禁，会显著恶化稳定性

当前无确切信息的部分：

- 当前仓库所有真实外部依赖测试所需的完整凭证矩阵
- 当前 CI 是否具备运行 GUI / 浏览器类发布冒烟的稳定环境
- 所有外部接口的代理、限流和超时策略是否已有统一约定

这些内容需要在实施阶段补充材料后再细化。

## 13. 验收标准

设计落地后，应满足以下验收条件：

- 默认门禁只运行稳定层测试，并能在本地和 CI 中重复通过
- `external` 与 `release-smoke` 拥有独立触发入口和独立失败解释
- 关键链路测试能在多个 sink 中复用同一个 `trace_id`
- 需要观测链路的测试失败后，能通过结构化日志与 payload 产物完成排查
- 历史“只打印不校验”的测试已被重写、迁出或降级为手工检查
- `backend/logger` 兼容层测试之外，普通测试代码不再继续依赖旧 `SugaredLogger`
